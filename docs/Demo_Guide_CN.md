# 这个项目怎么讲

这是一个使用 34 个虚构客户的 n8n 演示项目，展示“自动取数、规则检查、AI 写草稿、保存、人工审核”的过程。它可以放进作品集，但不应描述为已经服务真实客户的生产系统。

## 客户和数据从哪里来

客户是为演示编的测试案例，公司名称、联系人、互动次数和项目问题都是模拟资料。原始资料写在 Setup 工作流中，也保存在 demo_fixture.json。你运行一次 Setup（执行 93），程序就把 34 条客户资料和 34 条交付资料写入 n8n 数据表。后续定时工作流读取这些表，调用真实模型并保存草稿。

你没有手动上传 CSV。之前说明写成“手动导入 CSV”是文档错误，已改正。新整理的 Excel 和 CSV 是方便查看的副本，不是当时的导入文件；不用重新运行 Setup。

例如 C002 / Beacon Health：我们设定它有 2 次互动、健康评分 3 分、一个导出列顺序问题，以及 2026-10-15 的续约日期。系统据此生成回访邮件，你再阅读和批准。模拟的是客户资料，真实运行的是取数、模型生成、保存和审核流程。

## 30 秒介绍

我用 n8n 和 OpenAI 模型做了一个客户月度回访原型。系统从两张数据表读取 34 个模拟客户的活动及交付数据，检查风险规则并生成邮件或内部处理计划，把结果保存到审核队列。人在登录后的表单里查看原始事实和具体版本，再决定是否批准。我还保存了实际模型错误被拦截、记录和阻止进入待发送状态的证据。

## 展示顺序（约 2 分钟）

1. 展示审核清单：34 个客户，Green 10、Amber 12、Red 8、Review Pending 4。说明 Setup 已把内置的模拟资料写入数据表，工作流运行时自动取数。
2. 展示 C002：客户是 Beacon Health，当前版本引用为 GEN-98-C002-V1，草稿引用了上线日期、导出列顺序问题和续约日期。下方源事实便于人工核对。
3. 展示批准确认页：这个具体版本被批准并标记为 Ready for manual sending。页面明确写着没有发送邮件。
4. 展示执行 238 的失败记录：模型把“14 天未联系”误判为 Green，校验器阻止该批进入正常保存路径，记录 RUN_FAILED，并把八条记录标为 Processing failed / Not ready。

## 面试时解释为什么这么设计

- 自动触发：每次不需要再打开聊天框输入提示词；演示每两分钟检查一次。真正按月末工作日运行还需要另做日历配置。
- 数据表：把输入和输出保留下来，方便复查；本项目没有接入真实 CRM API。
- 固定规则与 AI 分工：模型先后在月初和 14 天边界上判断失误，所以 FIX03 改由代码计算明确的风险条件，AI 负责解释和个性化撰稿，校验仍保留。
- 人工审核：规则一致不代表语气、关系背景和行动建议一定适当；批准针对具体版本，新版本需重新审核。
- 失败处理：出现不合规则的输出时停止该批、留下记录、阻止其进入可发送状态，然后由人检查原因并控制恢复。

## 已完成与未声称完成的部分

全部 34 条保存输出已核验，来自执行 98、234、270、272、276，使用过不同配置和恢复尝试。当前 C002 批准由显示页和确认页截图支持，未再次提取批准节点原始 JSON。没有额外进行退回、修订、旧表单拒绝或网络超时测试，也没有客户邮件发送。

最终保存结果均符合给定分类规则，但这不能写成“AI 分类准确率 100%”：最后的混合设计把代码计算的标签提供给了模型。两次已核验的原始失败批次各有 7/8 分类与规则一致，不能据此估计通用模型准确率。没有测量业务耗时节省。

## 演示结束

在 Personal 的工作流列表里找到 Client Review Portfolio - 02 Scheduled processing，使用该工作流的操作菜单取消发布（Unpublish），停止两分钟一次的空检查。保留 03 审核工作流用于查看。此操作需要你在自己的 n8n 页面完成，本助手没有代为停用。
